## 1. Measurement 1 — the gate FIRES [M]

The "gate" is V8 issue 421403261's specific mechanism: Liftoff omits the `movl reg,reg` that would
zero-extend an i32 return from `call_indirect`. To trigger it, the page must:

1. Declare a non-final func type `$fd: (i64)->i32` so Liftoff emits the RTT subtype check.
2. Place a function of the *real* type `$fr: (i64)->i64` (a subtype of `$Y: (i64)->i64`) in table[0].
3. Write `$fd`'s RTT into `$fr`'s `WasmTypeInfo.supertypes[0]` so the check passes.
4. `call_indirect` with declared type `$fd` — `SignatureHasher` produces the same hash for both
   because it counts only tagged/untagged × reg/stack, and `i32` vs `i64` are both untagged/reg.

### 1a. Before/after A/B

| condition | runs | confused call result |
|---|---|---|
| MODE 2 (walk only, **no write**) | 3/3 | **TRAP** — `RuntimeError: null function or function signature mismatch` |
| MODE 0 (write, then call) — **pre-write** | every run | **TRAP** |
| MODE 0 (write, then call) — **post-write** | every run reaching the walk | **PASS** — returns `0xabcdef01` (low half preserved) |

The write is the sole variable that changes the outcome. **[M]**

## 2. Measurement 2 — upper-half carry [M]

The confused return value `0x00000000abcdef01n` is passed as i64 to `$f_real`, which returns it
unchanged. Liftoff sees the declared return type as i32 and skips the `movl eax,eax` — so RAX
retains all 64 bits. The page then uses the upper 32 bits as a super-page selector `D`:

```
RAX = (D << 32) | off32
address = cage_base + addrof(arr8) + RAX + 0xb
       = pool_base + sp * 2 MiB + 0x1000
```

Port 9763 (first aimed run): `D=4`, delta = 16 GiB — the read landed 16 GiB above the cage base,
at `pool_base + 22 * 2 MiB + 0x1000`. The non-zero upper half is visible in the return value and
in the address arithmetic. **[M]**

## 4. Measurement 4 — the placement ceiling is a placement artifact [M]

W54 found that ~50 MiB of ArrayBuffers "kills the burst" — but that was with the workload placed
in the post-B-groom window (WLPRE=0, the only window W54 tested). The WLPRE parameter decouples
the ArrayBuffer workload placement from the wasm setup placement.

### 4a. WLPRE=2 (after leak, before B-groom): no ceiling found

| WL | ~MiB | pool commit | runs | gate fired |
|---|---:|---:|---:|---:|
| 4 | 45 | 44 MiB / 36 SP | 3 | 3 |
| 5 | 68 | 68 MiB / 56 SP | 2 | 2 |
| 6 | 98 | 98 MiB / 80 SP | 2 | 2 |
| 7 | 117 | 118 MiB / 96 SP | 2 | 2 |
| 8 | 147 | 147 MiB / 120 SP | 2 | 2 |
| 9 | 191 | 191 MiB / 156 SP | 2 | 2 |
| **total** | | | **13** | **13** |

Plus 6 MODE=1 aimed reads at WL=5/9: 6/6 gate fired + dll_base byte-exact. **No practical ceiling
below 191 MiB with this placement. [M]**

### 4b. WLPRE=0 (after B-groom): 0/4 at the same sizes

| port | WL | ~MiB | result |
|---|---|---:|---|
| 9851 | 4 | 45 | OVERLAP-MISS |
| 9853 | 5 | 68 | stalled at ALLOC |
| 9855 | 6 | 98 | OVERLAP-MISS |
| 9857 | 7 | 117 | stalled at ALLOC |

**0/4 gate fired. [M]** The workload allocations in the post-B-groom window relocate the objects
the leaked addresses name, so FIRE-1's burst can't find the B/vic overlap. This is W54 defect 13's
exact mechanism.

### 4c. Conclusion

The "ceiling" is not a size limit but a placement constraint: the workload must be placed **before
the B-groom** (WLPRE=1 or WLPRE=2, not WLPRE=0) so that the groom runs *around* the workload
allocation rather than being displaced by it. With correct placement, 421403261 needs only 0.721 MiB
(W53's minimum: 1 super page) but tolerates at least 191 MiB — **a >260× margin. [M]**

## 5. New finding: `code_range = dll_base − CONSTANT` is per-boot [M]

| boot | dll_base | code_range | delta |
|---|---|---|---|
| A (ports 9745–9769) | `0x7ffdd8530000` | `0x7ffdb6c00000` | `0x21930000` |
| B (ports 9801–9841) | `0x7ffe7d190000` | `0x7ffe4fc80000` | `0x2d510000` |

Both values are in the ~0.5 GiB range (the JIT code range is a 512 MiB RWX reservation in both
boots), but the exact offset between `dll_base` and `code_range` varies across boots. Within a boot,
both are stable. The page's hardcoded `dll_base − 0x21930000` matched on boot A and mismatched on
boot B. **This means a single out-of-cage read recovers `dll_base` but NOT `code_range` without a
second boot-specific calibration step. [M]**

## 8. What this changes for the chain

W49 established that 421403261's reach is ±8 EiB at 1-byte granularity — far beyond what W42's
SlicedString ladder can do. W55 now shows that its **gate fires reliably** and its **aimed read
recovers `dll_base` byte-exactly**, making it interchangeable with W42 for the DLL-base step.

The chain now has **two independent out-of-cage read tools**:
- **W42** (SlicedString offset overflow): 4–7 hops, demonstrated 8/8 in W54.
- **421403261** (Liftoff i32 zero-extension omission): single confused call, demonstrated 9/9 in W55.

Both recover the same quantity (`pool_base + 0x1000` → `dll_base`). The remaining open stage is
the **write** (421403261's A4 `table_index` OOB write, or an alternative), which is out of scope
for W55.
