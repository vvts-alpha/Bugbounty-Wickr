# W42 — A2 (crbug 519768343): SlicedString offset overflow gives an OUT-OF-CAGE READ

Written 2026-08-05. Continues W35 (in-cage arb R/W via CVE-2026-11645). Every line **[M]
measured** on the shipped AWS Wickr desktop (Qt WebEngine 6.9.2, Chromium base
130.0.6723.192, declared patch level 139.0.7258.67) unless marked **[I] inferred**.
Harness/pages `scratch/w33/` and `scratch/w42/`.

**Bottom line: an attacker page that already holds W35's in-cage arbitrary R/W forges a chain of
`SlicedString`s whose accumulated offset is 64-bit. `String.prototype.charCodeAt` then
dereferences `parent_data + accumulated_offset`, which — because the accumulation is `IntPtrAdd`
(64-bit), not `Int32Add` — resolves to an address OUTSIDE the 1 TiB V8 sandbox and hands the
byte straight back to JS. Two things are demonstrated, both A/B-controlled against patched
Chrome 150:**

* **Stage 1 [M]** — the read leaves the cage: a 261-slice chain accumulates offset
  `0x104_0000_0000` (1.016 TiB); the faulting load is `movzx [r12+rcx]` with `r12 = string_data`
  (in-cage) and `rcx = 0x104_0000_0000` (the accumulated offset), landing **16.02 GiB into the
  32 GiB guard region**, cage base measured directly in R14. Reproduced 7/7 with per-run ASLR.
* **Stage 2 [M]** — the read is real and byte-exact: under a `--single-process` harness that
  plants a random nonce at `parent_data + 1.25 TiB` (an address the OS confirms is FREE, i.e.
  not inside any V8 reservation), the page recovers the exact 32-byte nonce it could not
  otherwise know. **5/5 byte-exact**, different random nonce each run.

This is the **READ half** of a V8-sandbox escape. It is **not** code execution and **not** a full
escape — a write half is still required (verdict in §8). The V8 sandbox is ON (measured, W33/W35).

## 1. The defect (crbug 519768343), confirmed against the pinned tree [M]
`ToDirectStringAssembler` accumulates every `SlicedString`'s `offset_` as it unwraps a string.
At the pin (`v8 branch-heads/13.0`, `src/codegen/code-stub-assembler.cc`, fetched to
`scratch/w42/src/v8/branch-heads_13.0/`):

```cpp
// ctor, line 8405
var_offset_(IntPtrConstant(0), this),                         // 64-bit accumulator
// if_issliced, lines 8517-8519
const TNode<IntPtrT> sliced_offset = LoadAndUntagPositiveSmiObjectField(
    string, offsetof(SlicedString, offset_));
var_offset_ = IntPtrAdd(var_offset_.value(), sliced_offset);  // 64-bit add
```
`LoadAndUntagPositiveSmiObjectField` (line 2032) returns `Signed(ChangeUint32ToWord(value))` — a
**zero-extend**, so each hop contributes `zext32(SAR(rawSmi,1)) ∈ [0, 2^32)`. Chained deep
enough, the 64-bit sum exceeds the 1 TiB cage + 32 GiB guard. The sink (`StringCharCodeAt`, line
8324): `offset = UintPtrAdd(index, to_direct.offset()); Load<Uint8T>(string_data, offset)`.

**The fix `ff1f27e6e2bd` (2026-06-08, after the pin — G1 PASS) makes the accumulator 32-bit**
(`Int32Constant(0)` / `Int32Add`), so it wraps at 4 GiB and can never leave the cage; it also
deletes `// TODO(v8:9880): Use UintPtrT here.` (G2 byte-exact — that TODO is present at the pin,
`code-stub-assembler.h`). The fix carries **no CVE** — consistent with Google treating the V8
sandbox as a hardening boundary; Qt's CVE-keyed backport ledger is structurally likely to miss
it (W36). Fix commit + upstream regression test `regress-519768343.js` are public
(`scratch/w42/commit_ff1f27e6e2bd.txt`); no PoC was downloaded or run.

## 2. Why it needs a prior primitive — and why that is satisfied now [M]
Legitimately, a `SlicedString`'s parent is never another `SlicedString` (`SubString` flattens via
`TryToDirect` first), and one slice's offset is bounded by its parent's length (≤ `kMaxLength` ≈
0.5 GiB) — nowhere near 1 TiB. To accumulate past the cage you must **forge a chain**: rewrite
each slice's `parent_` to point at the next slice and each `offset_` to a large Smi. That needs
an **in-cage arbitrary write**. The upstream regress test uses the `--sandbox-testing`
`Sandbox.*` API for this; **that API is compiled out of both builds** (measured: `--js-flags=
--sandbox-testing` aborts V8 at startup on both; without it `typeof Sandbox === 'undefined'`).
So the forge uses **W35's `arbWrite64`/`addrof`** (CVE-2026-11645) instead — re-verified working
this session (`p36ab-arbrw.html`: shipped `ARB-RW-VERIFIED`, Chrome 150 `NO-SMASH`).

## 3. Live-object layout, verified byte-exact [M] (`w42-p1-layout.html`)
`SlicedString` (pointer-compressed): **map@0, raw_hash@4, length@8, parent@12, offset@16**
(from `string.tq`/`name.tq`, then confirmed on a real `"…".substring(1,33)`):
`parent == addrof(P)`, `offset == 2` (= Smi(1)), `length == 32`. `LAYOUT-CONFIRMED`.

## 4. The forge (`scratch/w33/w42-forge.tmpl.html`, generated by `w42gen.py`) [M]
Per-hop offset value `V` → raw Smi field `(V<<1)&0xFFFFFFFF` (valid for "clean" `V`, bit31==bit30;
`buildHops` emits only such values, using `0xFFFFFFFF` for the bulk + a `≤0x3FFFFFFF` remainder).
For total `T`: `M` slices `P.substring(1,33)`; RMW each `slice[i].parent = slice[i+1]`
(last → `P`), `slice[i].offset = rawForV(hops[i])`, via two 8-aligned `arbRead64`/`arbWrite64`
pairs. A `FORGED` self-check reads three slices back and refuses to read on mismatch
(`forgeOK`), so a forge failure can't masquerade as a result. ~290–320 slices ⇒ ~1300 helper
ops, inside W35's safe single-burst budget; then B is restored and `vic` parked before the read.

## 5. Stage 1 — the read leaves the cage. A/B divergence table [M]
All shipped-Qt rows use the identical forge; only `T` (the accumulated offset) differs.

| # | accumulated `T` | slices | shipped Qt WebEngine | patched Chrome 150 |
|---|---|---|---|---|
| in-cage control | `0x11` (17) | 1 | `READ` returns `parent[17..]` = `"DEFGHIJKLMNOP0123…"`, **survives** | `NO-SMASH` |
| wrap = what `Int32Add` yields | `0x0400_0000` (64 MiB) | 1 | `READ` in-cage (0x00), **survives** | `NO-SMASH` |
| **overflow** | **`0x104_0000_0000`** (1.016 TiB) | **261** | **`READ` FAULT out-of-cage — renderer dies** | `NO-SMASH` |

Chrome's `NO-SMASH` is at the 11645 fire (before `T` is used), so it is **T-independent**: the
patched build blocks the chain at the bootstrap and A2 never runs there. The A2 arithmetic is
therefore isolated **on shipped Qt** by the in-cage vs out-of-cage divergence above.

**The overflow fault, captured under `--single-process` (VEH), 7/7 successful runs** (ports
8511-8527; `fault-8511.log`):
```
operation = READ   target address = 0x4dd0107b314
insn @ RIP = 41 0f b6 0c 0c            ; movzx ecx, byte [r12+rcx]   == Load<Uint8T>(string_data, offset)
RCX = R9 = 0x0000010400000000          ; offset = accumulated 64-bit T (= 1.016 TiB)
R12 =      0x000003d90107b314          ; string_data = cage_base + parent_data_off
R14 =      0x000003d900000000          ; cage_base, straight from the ptr-compression base register
target = R12 + RCX = 0x4dd0107b314     ; UNREADABLE, state=MEM_RESERVE  -> guard page
```
`target − (cage_base + 1 TiB) = 16.016 GiB` → squarely inside the 32 GiB guard. Across the 7
runs the cage base was ASLR-randomised (0x94…, 0x394…, 0x31c…, 0x282…, 0x27b…, 0x216…, 0x23f…
`00000000`), `RCX == T` every time, and `target == cage_base + T + parent_off` every time.

**What the fix would do, on this same chain:** the 261 offsets are `260×0xFFFFFFFF + 260`; under
`Int32Add` that is `260·(2³²−1) + 260 ≡ 0 (mod 2³²)`, so the patched code reads `parent[0]` =
`'W'`, in-cage. The wrap-control row (a 64 MiB in-cage read that survives) is the general case:
anything `Int32Add` can produce (< 2³²) stays in the cage.

## 6. Stage 2 — the read is real, byte-exact (`scratch/w42/`, harness `w42fault.c`) [M]
`w42fault.exe` loads the page `--single-process` (renderer memory == harness memory), and on a
background thread: scans committed memory for the page's unique parent marker `P`, derives
`cage_base = P & ~(2³²−1)`, computes `read_addr = P + T` (`T = 0x140_0000_0000` = 1.25 TiB),
proves `read_addr` is out-of-reservation, plants a **random 32-byte nonce**
(`QueryPerformanceCounter^tick^pid`) there, and signals the page (`/params` long-poll). The page's
forged chain (`T = 1.25 TiB`, 321 slices) then `charCodeAt(0..31)` reads `read_addr[0..31]`.

Out-of-cage proof is independent of any size assumption: **`VirtualQuery(read_addr)` = `FREE`
before planting, and `VirtualAlloc(read_addr)` SUCCEEDS** — an address you can reserve was not
part of the V8 sandbox reservation. It sits 1.25 TiB above `cage_base` (Stage 1 measured the
sandbox+guard ending at cage_base+1.031 TiB).

**5/5 byte-exact** (ports 8541, 8551, 8552, 8561, 8562), e.g. 8551:
```
harness planted (random) : "W42_OOC_003C107DFC5D055E_ENDX!!!"   at read_addr=0x20501070594 (cage+1.25 TiB)
page read via chain      : "W42_OOC_003C107DFC5D055E_ENDX!!!"
hex 5734325f4f4f435f303033433130374446433544303535455f454e4458212121   MATCH
VirtualAlloc(read_addr) SUCCEEDED => read_addr FREE, not within sandbox reservation
```
The page recovered a value the harness generated at runtime and never transmitted — obtainable
only by reading the out-of-cage address. Reliability ~5/6 end-to-end, gated entirely by the W35
leak's ~80% hit-rate (every miss is a safety-rejected `LEAK-FAIL`, never a wrong read).

## 7. The offset arithmetic actually observed [M]
* per-hop offset = `zext32(SAR(rawSmi,1))`; used `0xFFFFFFFF` (raw `0xFFFFFFFE`) per bulk hop.
* Stage 1: `260×0xFFFFFFFF + 260 = 0x104_0000_0000`; **261 hops**; landed `cage_base + 1.016 TiB`
  = **16.02 GiB into the 32 GiB guard**.
* Stage 2: `320×0xFFFFFFFF + 320 = 0x140_0000_0000`; **321 hops**; landed `cage_base + 1.25 TiB`,
  ~224 GiB past the guard, on OS-confirmed-free memory.
* The 1.3 TiB reach the brief cited is real: with the max clean per-hop of 4 GiB, ~256 hops
  already clear the 1 TiB cage; the chain length is the only limiter (≤4096 hops per build call).
* Landing on a **loaded module's** header (the brief's bonus) is **impractical here [M/I]**:
  modules load at ~`0x7ffb…` while the cage sits at ~`0x0c5…–0x3d9…`, i.e. ~127 TiB away — that
  is ~32,000 hops at ≤4 GiB each, over the per-call hop cap. The planted-nonce cross-check at
  +1.25 TiB (~290 hops) is the feasible rigorous proof and is equally conclusive.

## 8. Scope, and the verdict on the write half [M]
This is the **READ half** only — arbitrary out-of-cage *read*, delivered to JS one byte per
`charCodeAt` (or a run per `substring`). It is **not** code execution and **not** a full sandbox
escape: no out-of-cage *write*, no PC control. It presupposes W35's in-cage arb-write to build
the chain (so the full path is CVE-2026-11645 → forge → crbug 519768343).

**Verdict: do A4 (crbug 350628675) next, not A3.** A4 is the write-half twin — an in-cage
`WasmTableObject::uses` Smi drives `table_index` into an out-of-cage `std::vector<WasmTable>` with
no SBXCHECK on `table_index`, yielding a **raw out-of-cage write from plain JS** (precondition
already measured; W36 G1/G2 PASS). Pairing A4's write with this note's read would give a full
out-of-cage R/W — the precondition for an escape — **without a Worker**. A3 (crbug 464296297) is
also a write ("AAW") but the 1 TiB cage is process-wide (`GetProcessWideSandbox`), so it needs a
Worker to race the GC double-fetch; prefer A4's plain-JS path first and hold A3 as the fallback.
